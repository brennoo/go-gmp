# Current sprint tracker and design review

This document is the repository's current engineering tracker. It began as the August 2026 design
review and intentionally retains the detailed evidence and decision records below. Keep the status line
of each task and the sprint summary current when work lands; the older analysis remains useful context.
Line references and quoted code may drift, so trust the surrounding description over an old line number.

Severity: **P0** correctness/data-loss · **P1** API or protocol fidelity · **P2** ergonomics/hygiene.
Status: `todo` · `in-progress` · `done` · `deferred` · `wontfix`.

## Current sprint

schema-conformance and XML-fidelity oracles as adoption gates.

**Family selection method (this milestone):** ranked all ten create/get/modify command families against
the six candidate criteria (small generated response graph, few unexplained schema defects, findings
confirmed by both oracles, existing fixture coverage, limited public-API impact, create/get/modify shape)
by rank-summing four quantifiable proxies drawn from `internal/schema/testdata/CONFORMANCE.md` and the
fidelity corpus: combined `create_X`/`get_Xs`/`modify_X.go` line count (response-graph size), SCHEMA-DEFECT
count, `[fidelity]`-confirmed finding count, and total actionable finding count, with fixture-completeness
as a tie-break. `role` ranked first (score 11, vs. `group`'s 18 and `tag`'s 19.5) — smallest combined
source (83 lines), zero SCHEMA-DEFECT findings, the highest fidelity-confirmation ratio of any candidate,
and purely-additive findings (all `MISSING`/`TYPE`, no `EXTRA`/`KIND`), so adopting it carries no field
removal or type-restructuring risk. `permission`, one of the two families suggested at the start of this
milestone, ranked worst (score 31) once calculated rather than picked intuitively.

live fixtures and the upstream fixture drop their boolean `changed` mismatches (the
`Writable`/`InUse`/`Active` `"0"`/`"1"` → `"false"`/`"true"` re-encodes are now byte-identical), leaving only

`create_tag`'s own two request-fidelity fixtures regress, for two distinct and unrelated reasons:

- live/001 (`dropped=3`): this fixture's recorded request already carries `<resources><resource
  id="…"><type></type><name></name><trash>false</trash></resource><type>target</type></resources>` — empty
  `type`/`name` children plus a `trash` child under `<resource>`, a shape the narrower generated
  `TagResource{ID}` doesn't have room for and so drops on round-trip. This is not new protocol evidence: it is the *old*
  hand-written `TagResource` (which carried those same three fields) emitting them itself when
  `internal/gmptest/capture_sequence_test.go`'s `lifecycleTag` recorded this fixture against a live gvmd
  22.7, before tag's adoption. gvmd's 201 response shows it tolerated the extra empty elements, which is
  useful evidence on its own — but it is evidence of tolerance for historical client output, not evidence
  that `type`/`name`/`trash` belong on `<resource>` at all; the schema never declared them there. The
  narrower generated type is correct per-schema, and the fixture now correctly reports that fidelity loss
  instead of silently agreeing with a shape only the old client ever produced.
- upstream/001 (`dropped=1`, `added=2`, up from `added=0`): this is a genuine schema/example mismatch, not
  a generator regression. The upstream doc example puts `<resource id="…"><type>target</type></resource>`
  directly under `<create_tag>`, with no `<resources>` wrapper at all — a pre-wrapper GMP shape the current
  schema no longer describes (`resources` is a required wrapper with its own `type` and repeated
  `resource`). The bare `<resource>` was already unrecognized and dropped before this adoption; now that
  `Resources` is a required, always-marshaled value, re-encoding also emits an empty `<resources>` wrapper
  and its required `<type>` child that have no counterpart in the stale example, which is where the two new
  `added` paths come from.

Both are accepted as documenting real discrepancies rather than being patched over. Separately, the
`TestRequestGolden` cases in `internal/gmptest/cases_tag.go` for `active_false`/`active_unset` originally
left `Resources` at its zero value, which — now that it's required — produced a golden with a meaningless
empty `<resources><type></type></resources>`. Since the schema requires resources, the fix was to give all
three `create_tag` cases (`active_true`/`active_false`/`active_unset`) the same populated `Resources` value
and vary only `Active`, matching what those cases actually mean to test.

Correctly parsing `<id>` only gets the schema side right; representing two same-named schema children in one
Go struct still needed a codegen mechanism, since `encoding/xml` rejects two struct fields sharing one
explicit tag in both directions ("field X with tag filters conflicts with field Y with tag filters"), and the
only legal workaround — tagging the second field `xml:"-"` and driving it from a custom
`UnmarshalXML`/`MarshalXML` — has to be built, not declared. The direction chosen here was fully generic
auto-synthesis over a narrow per-case override: `internal/codegen/generate.go`'s `emitFields` now tracks wire
names seen among a struct's `KindElement` children and flags `collided = true` on a second occurrence,
tagging that field `xml:"-"`; `emitRequest`/`emitResponse`/`emitStruct` then call `emitCollisionMethods`,
which mechanically emits an `UnmarshalXML` that counts occurrences of the colliding wire name and routes the
Nth occurrence to the Nth field in declaration order, and a mirroring `MarshalXML` that encodes each field
with its own explicit `EncodeElement` call (bypassing the reflection-based tag lookup that rejects the
duplicate). Routing by occurrence order rather than by sniffing shape is safe because `<pattern>` is a
sequence and gvmd emits colliding elements in schema-declared order — confirmed on
`internal/gmptest/testdata/live/get_filters/001_response.xml`, whose `<filters id="">...</filters>` precedes
`<filters start="1" max="1000"/>`, matching the schema's declaration order exactly. `Generate()`'s public
signature is unchanged; no override table or hand-written support file was added. This changes exactly one
golden file in the whole corpus (`get_filters.go`, `Filters2` now `GetFiltersFilters` instead of a bare,
always-empty `string`) — every other family's `collided` stays `false`, verified by the full golden/compile
suite. `TestGetFiltersCollisionRoundTrips` (`internal/codegen/generate_test.go`) is the round-trip proof this
mechanism needed: it decodes the real fixture above into the generated `GetFiltersResponse` in a scratch
module, then re-marshals and re-decodes it, asserting both round trips land on `Filters.Term ==
"first=1 rows=10 sort=name"` with 3 keywords and `Filters2 == {Start: 1, Max: 1000}` — the exact fixture
values — proving the collision codec actually separates the two sibling `<filters>` elements correctly in
both directions.

A second review pass on the collision codec itself raised four more findings, three of them real bugs in the
first draft's `emitCollisionMethods`/`emitCollisionUnmarshal`/`emitCollisionMarshal`:

1. ~~Occurrence-order dispatch was not provably safe as a generic mechanism~~ — an intermediate fix required
   every collision member to be `schema.CardRequired`, which prevented omission-driven index shifting but did
   not satisfy fail-closed routing: a *reordered* document (both members present, but the pagination-shaped
   `<filters>` arriving first) would still be silently mis-routed, since dispatch never looked at the elements
   themselves. A third pass replaced occurrence-order dispatch entirely with **attribute-signature dispatch**.
   `collisionDiscriminators` computes, per collision member, the set of start-tag attribute names that appear
   on that member and no sibling (for `get_filters`: `id` for the search-metadata `<filters>`, `start`/`max`
   for the pagination one) and fails generation if a member has none (`"no attribute that uniquely identifies
   it"`, guarded by `TestCollisionRequiresAttributeDiscriminators`). The generated code gets one
   `classify<Type><Name>(attrs []xml.Attr) (int, error)` function per collision group, called from
   `UnmarshalXML` on every occurrence: it reports which member's signature the actual attributes match, and
   errors on zero matches (`"unrecognized ... element: no known variant's attributes are present"`) or more
   than one (`"ambiguous ... element: attributes match more than one known variant"`). The old occurrence
   counter is now a `seen[]bool` slice keyed by the classified index, so "unexpected extra occurrence" is still
   caught, but keyed off identity rather than arrival order. `TestGetFiltersCollisionRoundTrips` exercises the
   full matrix this implies: normal order (the real fixture), reversed order, each signature alone with the
   other member omitted, an unrecognized signature, and an ambiguous one — ten scenarios in total against one
   `go run` scratch program.
2. **`UnmarshalXML` never reset the receiver** — `*r = GetFiltersResponse{}` is now the method's first
   statement (before `r.XMLName = start.Name`), so decoding into an already-populated value can't leave stale
   data from whatever it held before. Proved by decoding two different fixture documents into the same
   variable and checking nothing survives from the first.
3. **`MarshalXML` unconditionally copied `r.XMLName` into `start.Name`**, so marshaling a zero-value
   `GetFiltersResponse{}` produced an empty root name and `encoding/xml` refused to encode it at all
   (`xml: start tag with no name`) — confirmed with a throwaway harness probing `encoding/xml`'s `defaultStart`
   fallback. `MarshalXML` now falls back to the literal schema root name (`get_filters_response`) when
   `start.Name.Local` comes back empty. `TestGetFiltersCollisionRoundTrips` gained a zero-value marshal
   assertion for this.
4. ~~The conformance oracle's MISSING/EXTRA acceptance hides real Go structure behind a comparer blind
   spot~~ — an intermediate response documented the gap in `validate_test.go`'s comments rather than closing
   it, which is not a fix. The actual fix is a private struct tag: a collision-routed field keeps its
   generation-mandated `xml:"-"` (the only tag `go vet`'s structtag analyzer accepts on a duplicate wire name)
   but also carries `gmpwire:"filters"` — a key `go vet` does not inspect, since its static check is scoped to
   the `"xml"` key specifically. `internal/schema/gomodel.go`'s `addField` now treats `xml:"-"` plus a
   non-empty `gmpwire` tag as visible under the `gmpwire` name instead of invisible (a field with a genuine
   `xml:"-"` and no `gmpwire` tag is unaffected); this needed no runtime coupling in either direction —
   `commands/*.go` gains no method, and `internal/schema` imports no concrete `commands` type, since a struct
   tag is read by name the same way the existing `"xml"` tag already is. That alone was not sufficient:

   `map[string]*GoNode` keyed on wire name, so both of the schema's `filters` occurrences looked up the same
   node. `walk` now keeps an occurrence-count cursor per name and pairs the schema's Nth child of a given wire
   name with the Go side's Nth field of that name, in declaration order — the same generalization

**`modify_permission.Name`/`.Comment` omit-vs-explicit-empty: experiment attempted, blocked by a gvmd bug.**
`modify_permission.Name`/`.Comment` are plain `string,omitempty` today, the same starting point
`modify_alert`/`modify_filter`/`modify_tls_certificate` each had before a live gvmd experiment proved
omit-vs-explicit-empty was a real, distinct wire semantic for their own `Name`/`Comment` fields. Per the
policy established for those three families, the same experiment was attempted here (throwaway
`//go:build integration` test creating a subject user and a permission, then running the omit/explicit-
empty/set matrix against `modify_permission`, read back via `get_permissions`) — but every real
`modify_permission` invocation against the live gvmd instance under test (`greenbone/gvmd`, `stable` tag,
confirmed current via a fresh image pull with no digest change) crashes the gvmd worker process before a
result can be observed.

Root cause, confirmed against `gvmd`'s own source on GitHub (`src/manage_sql_permissions.c`, present on
`main`): `permission_resource_id`/`permission_subject_id` query columns named `resource_id`/`subject_id`,

handler calls both functions on the path GMP XML clients actually take (`<subject id="...">`/

so the query fails with a plain `column "resource_id" does not exist` (or `subject_id`) Postgres error.
gvmd does not check for that failure and keeps issuing queries against the now-aborted transaction, which
eventually kills the worker (`Received Aborted signal`; the client sees `transport: EOF`). This was
confirmed reproducible and unconditional across three independent request shapes (comment-only, name-only,
resource-scoped and resourceless permissions), confirmed present in the Postgres logs from a full day before
this experiment (not something the experiment triggered), and independently corroborated by
python-gvm issue #1047, which reports the same "Error in SUBJECT" / crash symptom against `modify_permission`.
A Postgres lock and a stale Docker image were both raised and ruled out directly against the running
containers before this conclusion was reached.

`<comment>`) returns `400 Error in SUBJECT` — despite the schema declaring `<subject>` `CardOptional` (see
`internal/codegen/testdata/schema/modify_permission.json`). This is independent of the crash above (it
still occurs when the crash is avoided by always including `<subject>`) and is recorded here rather than
acted on, since the generated `Subject *PermissionSubject` already matches the schema's own declared

## P0 — Transport correctness

### T-1 · Read loop hangs forever on responses that are an exact multiple of 1024 bytes
**Status:** done · **File:** `connections/internal/implementation/conn.go:32-49`

`performRequest` reads into a 1024-byte buffer and treats `n < 1024` as end-of-message. A complete
response of exactly 1024 (or 2048, 3072, …) bytes issues another `Read` that blocks forever, because
the server has already said everything it intends to say. With no context deadline — the default for
most of the API, see T-3 — this never returns.

**Verified:** a synthetic well-formed 1024-byte response blocks `Execute` indefinitely (>3s, no deadline → forever).

This is not a corner case. Response sizes are chosen by the server, not the client, so roughly 1-in-1024
responses of arbitrary size land on the boundary.

**Fix:** stop using read-length as a framing signal. Frame on the XML document itself, precisely:

1. Feed the socket (through a persistent `bufio.Reader` held on the `Connection`, not a fresh one per
   call — see point 4) into an `xml.Decoder`.
2. Skip tokens until the first `xml.StartElement`. A decoder can legally emit `ProcInst`, `Directive`,
   `Comment`, or whitespace `CharData` before the root element while depth is still zero; a depth
   counter that starts counting immediately can terminate before the document even begins.
3. Track depth from that first `StartElement`; finish when its matching `EndElement` is consumed
   (depth returns to zero *after* having gone positive).
4. **Hold a long-lived `bufio.Reader` on the `Connection` and hand *that* to the decoder. A fresh
   `xml.Decoder` per call is fine.** The mechanism that makes this safe is specific and worth stating,
   because getting it wrong strands bytes: `xml.NewDecoder` checks whether its argument implements
   `io.ByteReader` and, if so, consumes from it directly byte-at-a-time; if not, it wraps the reader in
   its *own* internal `bufio.Reader`. `*bufio.Reader` implements `io.ByteReader`. So passing the
   persistent `*bufio.Reader` keeps the decoder from buffering behind your back. Passing a raw
   `net.Conn` instead means any over-read is stranded inside the decoder and unrecoverable when you
   discard it.

   **Measured on Go 1.23** (real TCP socket, both documents delivered in a single `Write`): after
   framing one document from a persistent `*bufio.Reader`, `Buffered()` holds exactly the following
   bytes, and a second fresh `xml.Decoder` over the same reader frames the next document correctly.
   With a non-`ByteReader`, the same trailing bytes are unrecoverable.

   **Treat that as a property of the toolchain we test against, not a contract of `encoding/xml`.**
   Nothing in the `xml.Decoder` API promises that `Token()` returning the root's `EndElement` leaves the
   underlying reader positioned precisely after its closing `>`; that it does today is an implementation
   detail. It's a sound basis for an implementation, but not for a documented public guarantee. Pin it
   with regression tests that fail loudly if a future Go release changes the read positioning, and don't
   let any exported behavior depend on byte positioning that we can't assert.

   Note this is *insurance, not a known requirement*: GMP is strict lockstep (T-2), so a well-behaved
   server should not have sent the next response before receiving the next request, and no unsolicited
   server-push message is documented. The persistent reader costs nothing and removes a whole failure
   class, but do not justify it with pipelining that isn't established — and correspondingly, **do not
   write a test asserting that post-document bytes are preserved across `Execute` calls**, since that
   test would be encoding a protocol behavior we have not confirmed is legal. Test the framing itself:

   - a document split across arbitrary socket read boundaries;
   - leading XML declaration, comments, and whitespace before the root;
   - documents of exactly 1024 bytes and exact multiples of 1024 (the original bug);
   - nested and self-closing elements;
   - malformed and truncated XML (must error, not hang — see T-13 for the poisoning consequence);
   - context deadline firing while awaiting the closing root element.

   Also pair this with T-2's mutex: reader reuse is only coherent if reads and writes are strictly
   ordered.
5. **Decide the `RawXML` contract before implementing byte capture.** Today `RawXML` returns
   `performRequest`'s bytes unmodified — no `xml.Marshal` round-trip — so exact fidelity is the current
   de-facto behavior, and only becomes a question because moving framing into the decoder could silently
   change it. Either explicitly document that `RawXML` returns the received document without guaranteeing
   lexical identity, or preserve exact bytes deliberately.

   If exact bytes are wanted, the clean way is a small **recording `io.ByteReader`** that wraps the
   persistent `*bufio.Reader` and appends each byte as the decoder consumes it. Because the decoder pulls
   byte-at-a-time from a `ByteReader` (point 4), the recorder ends up holding precisely the document's
   bytes — no `InputOffset()` arithmetic, no tee-buffer slicing, and nothing to replay into the next call.

   **Measured:** with two responses arriving in one socket write, this yields byte-exact capture of each
   document in turn (captured length equals `InputOffset()` both times). Avoid the `io.TeeReader` +
   `InputOffset()` slicing approach — a tee placed under the decoder records whatever the *reader* pulled
   rather than what the decoder consumed, which then does require offset arithmetic and suffix replay to
   stay correct. The recorder sidesteps that entirely.

   **The capture boundaries need to be part of the contract, because the recorder is not symmetric.**
   Framing (step 2) deliberately skips tokens before the root, but the recorder starts at the first byte
   the decoder *consumes*, which is earlier. Measured behavior:

   | stream | captured |
   |---|---|
   | `<?xml version="1.0"?>\n<!-- hi -->\n<a>x</a>` | the whole thing, declaration and comment included |
   | `<a>1</a>\n<b>2</b>` (2nd doc) | `"\n<b>2</b>"` — leading newline belongs to no document |
   | `"  \n<a>1</a>"` | `"  \n<a>1</a>"` — leading whitespace included |
   | `<a>1</a>   \n` | `"<a>1</a>"` — trailing whitespace correctly left in the reader |

   So leading declaration/comments/directives *are* captured, leading whitespace is *also* captured, and
   trailing whitespace is correctly excluded. **Pick exactly one of these contracts — do not
   "left-trim", which an earlier draft suggested.** Trimming is neither exact wire fidelity nor clean
   document extraction: it invents an asymmetry between leading and trailing whitespace and can alter
   content ahead of the declaration. The coherent options are:

   - **Wire segment** — every byte consumed while locating and framing the document, inter-document
     leading whitespace included. Simplest to implement (it is what the recorder already does) and the
     most honest name for it, but the returned string is not always a standalone well-formed document.
   - **XML document** — from the XML declaration if present, else from the first markup belonging to the
     root; requires an explicit rule for comments and directives that precede the root.
   - **Root element only** — from the root's `<` through its matching `>`, discarding declaration,
     comments, and directives entirely. Cleanest to specify, loses the declaration's encoding info.

   Whichever is chosen, document it on `RawXML` and assert every row of the table above in tests, rather
   than leaving the boundary to whatever the decoder happens to do.

This subsumes the bug rather than patching it, and removes the accidental 1024-byte buffer size as a
correctness-relevant constant altogether.

### T-2 · `Connection` is not concurrency-safe, and concurrent use deadlocks
**Status:** done · **File:** `connections/internal/implementation/conn.go`

There is no mutex anywhere in the package. GMP is a synchronous request/response protocol over a raw
socket with no request/response correlation IDs, so two goroutines sharing one `Connection` will read
each other's replies off the wire.

**Verified:** 50 goroutines issuing `Execute` on one shared `Connection` over a real TCP socket deadlock
permanently — goroutines consume responses belonging to other goroutines, and the ones left with nothing
to read block forever in `Read`. (An earlier probe over `net.Pipe` showed no failure; `net.Pipe` is
synchronous and unbuffered, so it accidentally serializes callers and masks the bug. Any test of this
must use a real socket.)

This matters because `client.New(conn)` returns one long-lived client that users will naturally share
across goroutines, and nothing in the docs says not to.

**Fix:** serialize the complete write-then-read transaction, so that only one request occupies the
socket at a time (the admission primitive is T-2b's call). Specifics that are easy to get wrong:

- **`RawXML` must be inside the same critical section as `Execute`.** `RawXML` calls `performRequest`
  directly (`conn.go:92-98`) on the same socket, so serializing only `Execute` leaves `RawXML`/`Execute`
  and `RawXML`/`RawXML` pairs with the identical response-stealing bug. Acceptance criterion: one
  admission gate covering the full transaction of *both* entry points.
- **The existing cancel-goroutine becomes actively dangerous once requests are serialized.** `Execute`
  currently spawns a goroutine that closes `rawConn` on `ctx.Done()` (`conn.go:60-69`). If that
  goroutine is armed *before* the caller is admitted to the transaction, a queued caller whose context
  is cancelled will close the socket out from under whichever goroutine is currently mid-request —
  turning one caller's cancellation into an unrelated caller's transport failure. Close-on-cancel must
  only be armed once the caller owns the transaction and the request is genuinely in flight.
- **`SetRawConn` must be setup-only** and documented as such: it swaps the socket with no
  synchronization and must never race with an in-flight request.

Then decide and document the overall concurrency contract: serializing makes a shared client safe but
serial; a connection pool would be needed for genuine parallelism (and each pooled connection needs its
own authentication). Document the chosen guarantee in the README either way.

**Admission, connection state, and `Close` semantics are specified in T-2b, which must be settled
first** — they determine which primitive does the serializing above.

### T-2b · Unified connection lifecycle: admission, state ownership, and `Close`
**Status:** done · **Blocks:** T-2, T-13 · **File:** `connections/internal/implementation/conn.go`

**Four corrections found after the first implementation landed.** Recorded here because each one is a
design decision the original entry did not settle, not merely a coding slip:

1. **A `select` between `ctx.Done()` and a completion channel is not a decision procedure.** When both
   are ready Go picks at random, so a cancellation arriving strictly *after* a successful transaction had
   roughly even odds of poisoning a healthy connection. Resolved with an explicit mutex handoff
   (`outcomeMu`/`cancelled`/`finished`) where the owner publishes completion before signalling.
2. **Publishing completion cannot be made atomic with the end of I/O.** The watchdog is a separate
   goroutine reacting to an event outside the package's control, so a window remains between
   `performRequest` returning and the owner claiming the outcome. Cancellation landing in that window
   poisons a connection whose transaction *did* succeed, producing `ioErr == nil && wasCancelled`.
   Classifying on `ioErr` alone reported success while silently handing back a destroyed transport. The
   window is not closable; the outcome is reconciled instead, and the caller is told the cancellation
   took effect.
3. **An already-cancelled context must be refused at entry, not handed to the watchdog.** Otherwise the
   watchdog fires immediately and closes the socket — so a single caller passing a stale context
   permanently destroys a connection *shared by everyone else*, with no reconnect path (T-13). Nothing
   has been written at that point, so there is no boundary ambiguity and nothing to poison. This is the
   same row of the table as cancel-while-waiting. The entry guard also runs before `xml.Marshal`, so a
   lifecycle error outranks a marshalling error and a custom `MarshalXML`'s side effects never run on a
   connection that has stopped accepting work.
4. **The socket is installed only at construction.** The original `SetRawConn` setter could not reset
   lifecycle state, so it half-reopened a retired connection: new socket, still-terminal state. Replaced
   with `implementation.New`. This is not just tidiness — it enforces T-13's rule that recovery happens
   on a fresh connection, because resuming a stream that failed ambiguously is exactly what lets the next
   call read the tail of a previous response and mistake it for its own.

**Admission is a semaphore, not a queue.** Waiting callers are not served FIFO and there is no starvation
bound; a caller arriving as the socket falls idle may take it ahead of one that waited far longer. Fine
for the intended usage (a bounded number of goroutines, short transactions), but it is a property to
document rather than imply, and callers needing fairness must arrange it above this type.

**Known, accepted trade-off: correction 2 poisons on timing, not on ambiguity.** When the document has
already framed (`ioErr == nil`) the boundary *is* known; the connection dies only because the watchdog
closed the socket inside the completion window. Safe and consistent, but a caller can lose a healthy
connection to a race it did not cause.

The alternative is deadline-driven cancellation: `SetReadDeadline(past)` instead of `Close()` unblocks a
pending read without destroying the socket, and `performRequest` already resets deadlines per call. Only
the race-window case would survive; in-flight cancellation would still poison.

**Not adopted:** `Close` is a guaranteed interrupt, deadlines are not — honoring `SetReadDeadline` is the
`net.Conn` implementation's choice, and wrappers and test doubles routinely stub it out, so cancellation
would go from "always works" to "hangs forever". `crypto/tls` also treats a connection as unusable after
a read error, so the common in-flight case gains nothing. Revisit only with a transport abstraction that
states interruption semantics contractually.

T-2 (serialize the transaction), T-13 (poison the connection on ambiguous failure), and cancellation all
mutate or read the same connection state, and specifying them independently produced a contradiction in
an earlier draft of this backlog: T-2 proposed a channel semaphore for context-aware admission while
T-13 proposed guarding state with "the same mutex that serializes the transaction" — but if admission is
a channel, there is no such mutex. **One design owns all of it. Settle this before writing any transport
code.**

Proposed design (adopt or replace as a whole, not piecemeal):

- **Admission: a size-one buffered channel used as a semaphore**, not a `sync.Mutex`. A `sync.Mutex`
  cannot be acquired with a context, so a queued caller cannot honor its own deadline; with a channel the
  caller `select`s on acquisition vs. `ctx.Done()` and returns `ctx.Err()` without ever touching the
  socket or disturbing the in-flight request. This is the reason to prefer it — cancellation while
  queued is the common case under a shared client.
- **State: a separate `sync.Mutex` guarding `rawConn` and a three-value state** (`open` / `broken` /
  `closed`). Separate from admission because `Close` must be able to act while another goroutine holds
  the transaction.
- **Only the transaction owner may transition `open → broken`.** Poisoning is a conclusion about a
  request that goroutine performed; no one else is in a position to draw it.
- **`Close` publishes the transition under the state lock but performs the actual socket close outside
  it**, and does not wait for the admission semaphore. `net.Conn.Close` is itself I/O and a custom
  `net.Conn` may block or re-enter, so holding the lock across it risks the same stall this design is
  meant to prevent. Sequence: lock → transition to `closed` and copy the socket → unlock → close the
  copy. Idempotency still holds, because the state transition is published before the underlying call.
- **Never hold the state mutex across blocking network I/O.** Take it to read/mutate state, release it
  before reading or writing the socket. Otherwise `Close` blocks behind exactly the hung request it
  needs to interrupt — which is the T-1 failure mode all over again.
- **The transaction owner must snapshot `rawConn` into a local, never re-read the field.** Releasing the
  state lock and later touching `conn.rawConn` again is a data race with `Close`/`SetRawConn`. Required
  sequence, and the acceptance criterion for the race detector:
  1. acquire admission (context-aware);
  2. under the state lock: verify state is `open`, copy `rawConn` to a local;
  3. release the state lock;
  4. perform *all* transaction I/O through that local — never the struct field;
  5. reacquire the state lock to classify the outcome and update state.
- **`closed` outranks `broken`** when reporting final state: an explicit `Close` is the caller's own
  action and is the more useful thing to be told about. Every transition to `broken` is therefore
  conditional on the current state still being `open`.

**Cancellation transitions, which "`closed` outranks `broken`" alone does not pin down:**

| situation | state transition | what the caller gets |
|---|---|---|
| Cancelled while queued for admission | none — the socket was never touched | `ctx.Err()` |
| Cancelled during in-flight I/O | `open → broken` (close the socket; boundary is ambiguous) | error wrapping `ctx.Err()`, not the bare platform "use of closed connection" |
| Cancelled after an explicit `Close` already set `closed` | none — `closed` is terminal | closed-connection error |

The in-flight row is why cancellation is an exception to "only the transaction owner may transition
`open → broken`": the cancel path acts on behalf of that owner and must take the state lock to do it,
using a compare-and-set against `open` so it cannot clobber a concurrent `Close`.

`Close` contract, which the current code leaves entirely undefined:

| question | contract |
|---|---|
| Concurrent `Close` while a request is in flight? | Safe. Transitions to `closed` and closes the socket immediately; does **not** block waiting for the request to finish. |
| What does the in-flight request see? | Its socket op fails; it returns a transport error, wrapping the close cause where the platform surfaces one. |
| What do queued/subsequent callers see? | A stable "connection closed" error, returned **before** any write is attempted. |
| Repeated `Close`? | Idempotent — second and later calls return nil (or a consistent sentinel), never a double-close panic. |
| Socket already closed by the cancel-goroutine? | Still transitions to `closed` and returns nil; the underlying already-closed error is swallowed, not surfaced as a `Close` failure. |

Both `Execute` and `RawXML` check state at entry and refuse to write when not `open`.

### T-3 · `context.Context` is ignored by most of the client surface
**Status:** done · **File:** `client/client.go`

Verified counts: `client.go` (interface) declares 130 methods, `client/client.go` implements 147
concrete methods (some interface methods are backed by a `*Raw` + wrapper pair), and
`context.Background()` is hardcoded at 105 call sites. Only the filtered `Get*` methods and the `*Raw`
variants accept a caller-supplied `ctx`. Every `Create*`, `Modify*`, `Delete*`, `Start*`, `Stop*`,
`Resume*`, `Verify*`, `Sync*` method hardcodes `context.Background()` instead. Callers cannot set a
timeout or cancel these calls even though the transport layer fully supports deadlines and
cancellation.

Combined with T-1, a hung request on any of these methods is unkillable.

`RawXML` has the same problem at both layers — `gmp.Connection.RawXML(xml string) (string, error)`
(`connection.go:8`) and `gmp.Client.RawXML(xml string) (string, error)` (`client.go:169`, implemented at
`client/client.go:695` as a thin pass-through to the connection). Neither accepts a context, and both
need the same fix.

**API shape must be decided explicitly, not left as "thread ctx through":**

- `ctx context.Context` becomes the first parameter on every method, no exceptions. This includes
  `Authenticate`, `DescribeAuth`, and `ModifyAuth`, which are currently also `context.Background()`
  call sites and easy to overlook because they read as "setup" rather than "requests."
- `RawXML` becomes `RawXML(ctx context.Context, xml string) (string, error)` on both `gmp.Connection`
  and `gmp.Client`.
- Old `context.Background()`-hardcoded signatures are removed, not retained alongside new ones.
  Keeping both (e.g. via a `*WithContext` twin for every method) doubles the interface surface
  permanently for a library that hasn't hit v1 yet; the README already accepts breaking changes at
  this stage.
- Lands in the same breaking release as T-6a, so the API break is one deliberate event rather than two.

### T-4 · TLS connection API cannot express real deployments
**Status:** done for TLS · **deferred for Unix** — see below · **File:** `connections/conn_tls.go`,
`connections/tls_options.go`

Landed as the breaking replacement: `NewTLSConnection(ctx, address, opts ...TLSOption)`. `ctx` also
replaced the hardcoded `context.Background()` in the dial, which is why there is no `WithDialTimeout` —
the caller's context already covers it. Defaults stay secure: verification on, `MinVersion` TLS 1.3,
with `WithMinVersion(tls.VersionTLS12)` as the explicit opt-out for older servers.

**Unix options were scoped out, not delivered.** `NewUnixConnection(ctx, socket)` took the `ctx` change
only. This entry above anticipated an additive `opts ...UnixOption`, and that part is not done: `ctx`
covers the deadline, but a custom dialer, a socket control function, or a local address cannot be
supplied. The judgement was that those are thin for a Unix domain socket — keepalive and local address
are meaningless there — so the remaining real case is a `Control` func for sandboxed environments. Cheap
to add later as a purely additive change, since there is no positional argument to displace. Recorded
here rather than silently marked done.

`NewTLSConnection(address string, insecure bool)` is a closed two-argument API that hardcodes its
entire `tls.Config`. It cannot express:

- **Client certificates.** gvmd commonly authenticates clients by certificate, and this repo's own
  test harness ships `hack/CA/clientcert.pem` + `clientkey.pem`. There is no way to present them.
- **TLS 1.2 servers.** `MinVersion` is pinned to `tls.VersionTLS13`. This repo's own
  `hack/docker-compose.yml` starts gvmd with `--gnutls-priorities=...:+VERS-TLS1.2:+VERS-TLS1.3`,
  and plenty of real installs are TLS 1.2 only. Those servers are simply unreachable, with no override.
- A custom CA pool (so the only way to talk to a self-signed server is to disable verification entirely
  — every example in the repo passes `insecure = true`, which is the wrong thing to teach).
- Dial timeouts, a custom dialer, or `ServerName` for SNI/hostname override.

**Migration strategy must be decided explicitly — this cannot be a compatible change for `NewTLSConnection`.**
Go has no overloading, and `insecure bool` as a required positional second argument cannot coexist with
a variadic functional-options signature under the same name: `NewTLSConnection(addr string, insecure
bool)` and `NewTLSConnection(addr string, opts ...TLSOption) (gmp.Connection, error)` are simply
different functions with an incompatible second parameter position. Pick one:

- **Breaking replacement** (recommended): change `NewTLSConnection`'s signature outright —
  `NewTLSConnection(address string, opts ...TLSOption) (gmp.Connection, error)`, with
  `WithInsecureSkipVerify()`, `WithClientCert(...)`, `WithRootCAs(...)`, `WithDialTimeout(...)` as
  options, defaulting to secure. The README already accepts breaking changes at this stage
  (`> [!CAUTION] Expect breaking changes`), and this is small enough to land in the same breaking
  release as T-3/T-6a rather than justify its own deprecation cycle.
- **Alternative, if a compatible path is required:** add `NewTLSConnectionWithOptions(address string,
  opts ...TLSOption)` alongside the existing function, and deprecate (`// Deprecated:`) the old one for
  a release or two before removing it.
- **Alternative:** replace the two positional args with a single config struct,
  `NewTLSConnection(address string, cfg TLSConfig)`, and add a `DefaultTLSConfig()` / `InsecureTLSConfig()`
  helper. Less idiomatic Go than functional options but is still one unambiguous breaking change rather
  than an option pattern retrofitted awkwardly onto an existing bool.

Whichever is chosen, apply the same decision to `NewUnixConnection(socket string)` — note this one
*can* take a purely additive `opts ...UnixOption` (e.g. `WithDialTimeout`) without breaking existing
call sites, since it has no positional bool to displace; it doesn't have to follow T-4's TLS-side
breaking change on the same timeline.

### T-5 · Inconsistent `bool` vs `*bool` makes some request fields impossible to set to `false`
**Status:** done · **Scope:** request-reachable optional scalar policy completed — see the execution addendum below

**Agreed scope (decided, do not re-litigate):** convert buckets 1 and 2 — fields directly on
request-root structs, and fields on dual-use nested types. Leave the response-only fields alone; that is
a separate design question about distinguishing "server sent `false`" from "server omitted the field",
and folding it in would triple the diff for a non-bug.

**Corrected counts.** A mechanical re-derivation (request-root = exactly the types appearing as
`cmd *commands.X` in `client/client.go`) gives **37**, not the 41 this entry claimed below as "exact and
reproducible". The 103 `bool ... omitempty` matches partition as: 5 already `*bool`, **37** request-root,
**15** dual-use nested, 3 request-only nested, 43 response-only. Note `ModifyConfigFamily` is listed
below in the dual-use bucket but is not reachable from any response — it is request-only.

**Also found, not in the original entry:** `Ultimate` is inconsistently tagged across siblings. Sixteen
`Delete*` commands declare `Ultimate bool` with `xml:"ultimate,attr"` and **no** `omitempty`, so they
always emit the attribute; only `DeleteTarget` and `DeleteTask` carry `omitempty` and therefore silently
drop it when false. Any blanket `Ultimate → *bool` change sweeps all 18 in, so decide that explicitly.

**Why it waits for T-9.** Request-vs-response reachability is exactly what the schema knows and grep
heuristics only approximate — the 41-vs-37 discrepancy above is that gap showing up in practice. The
call-site blast radius is small (~21 assignments, confined to `client/*_test.go` and two examples), so
the cost of waiting is low. Note the `false` call sites are precisely the ones silently broken today, so
their golden XML assertions change too, not just the struct literals.

**Ergonomics prerequisite:** there is no `Bool(b bool) *bool` helper anywhere in the repo, which is
probably why the existing `*bool` fields never spread. Add one alongside the conversion.

`encoding/xml` omits `false` for a plain `bool` field tagged `omitempty`, so on a request struct like
`CreateTask.Alterable bool \`xml:"alterable,omitempty"\`` there is no way to explicitly send
`alterable=0` — the caller silently gets the server default instead. A minority of fields already use
`*bool` (`CreateReport.InAssets`, `ModifyReportFormat.Active`), which is the correct pattern for a
tri-state (unset / true / false), so the codebase is inconsistent with itself.

**On the count:** `grep -rn 'bool.*omitempty' commands/*.go | grep -v _test` returns **103** matches,
but that figure conflates three different situations and only one of them is a functional bug.
Classifying each hit by whether its enclosing struct is ever marshalled as an outbound request
(cross-referenced against every `cmd *commands.X` parameter in `client/client.go`):

| category | count (of 103) | is it a bug? |
|---|---|---|
| direct field on a request-root struct (`GetTasks.Trash`, `CreateTask.Alterable`, …) | **41** | **Yes** — caller cannot express `false`/send the attribute explicitly. |
| field on a **dual-use** nested type reachable from both a request and a response (`TaskConfig`, `PermissionSubject`, `ModifyConfigFamily`, `Agent`, …) | **~14** | **Yes, on the request side** — same bug when the type is used to build a request. Converting to `*bool` is safe for decoding (unmarshal ignores `omitempty`) but changes the field's zero value from `false` to `nil` everywhere the type is used, including response consumers — audit call sites. |
| field on a response-only struct/type never referenced from a request (`Note`, `Override`, `Tag`, `PortList`, `Target`, `GetTasksResponseTask`, …) | **~48** | **No.** `omitempty` only affects marshalling; it is inert on a type that's only ever unmarshalled. This is dead/misleading tag noise, not a correctness defect. Converting these to `*bool` is a legitimate design improvement (lets a caller distinguish "server sent `false`" from "server omitted the field") but is a separate, lower-priority decision from the request-side bug. |

(Counts for the second and third buckets are from a one-off classification script, not exact to the
field — treat them as approximate; the request-root figure of 41 is exact and reproducible from
`client/client.go`'s parameter types.)

**Fix, in order:**
1. `*bool` for the 41 fields directly on request-root structs — this is the actual bug and the only
   urgent part.
2. For the ~14 dual-use nested types, same fix, but audit every call site (both request-building and
   response-reading code) since the field's Go zero value changes.
3. Response-only fields: drop the inert `omitempty` (cosmetic) and decide *separately*, on its own
   merits, whether `*bool` is worth it for those — do not fold this into the same change as (1)/(2).

Best enforced mechanically via T-9 (codegen), which can derive request-vs-response reachability from
the schema directly instead of grep heuristics.

**Addendum (2026-08-09) — T-5a–f, executed ahead of T-9 rather than waiting on it.** The bucket-1/2 fix
above shipped as two commits: bucket 1 (37 request-root fields → `*bool`, plus a `Bool()` helper), then a
follow-up once it became clear a plain `*bool` wasn't sufficient — gvmd's `boolean` schema type is lexical
free text ("zero is false, anything else is true... empty string is considered true"), which Go's
`true`/`false` string marshal doesn't produce. Fixed with a custom `GMPBool` marshal type
(`commands/bool.go`) applied to all 41 affected fields, since a bare pointer only solves the
tri-state/`omitempty` problem, not the wire-format problem.

The identical `omitempty`-drops-a-meaningful-zero bug shape then turned up in numeric fields (T-5c): 21
request-root `int`/`float64` fields converted to `*int`/`*float64` with new `Int()`/`Float64()` helpers
(e.g. `create_task.SchedulePeriods: 0` means "no limit"; gvmd documents `modify_agents.HeartbeatInterval:
0` as valid). A dual-use variant was attempted on `ReportHost.ResultCount`/`ComplianceCount` and
`ReportResult.OriginalSeverity`, then reverted after review flagged that those types are also
`GetReportsResponse`'s response types — the pointer conversion silently changed the public response API
for existing consumers. Decided to keep those 3 fields as plain `int`/`float64` (accepting that
`CreateReport` can't express an explicit zero for them) rather than break response callers.

T-5d asked whether the schema's `decimal` type has the same lexical-marshal risk as `boolean` did:
`xsd:decimal`'s lexical space forbids scientific notation, and Go's default `float64` XML marshal does
emit it at extreme magnitudes (confirmed empirically — `1e21` marshals as `1e+21`, `1e-7` as `1e-07`).
**Finding: no fix needed.** `decimal` appears in exactly 14 places in `GMP.xml.in`, all EPSS
`score`/`percentile` fields, all response-only — the only Go fields involved
(`ResultNVTEPSSInfo.Score`/`Percentile` in `commands/get_results.go`) are unmarshal-only, and the
scientific-notation defect is marshal-side, so it never triggers. `internal/schema/parse.go`'s `real` →
`decimal` type alias is dead (zero uses in the schema). Separately, `severity` — the type behind the T-5c
`Float64()` fields — is a distinct schema type with its own strict pattern
(`-[1-3](\.0)?|[0-9](\.[0-9])?|10(\.0)?`, range -3.0 to 10.0), which is nowhere near Go's
scientific-notation threshold, so those fields were never at risk either.

T-5e asked the same lexical-marshal question of timestamps, and unlike T-5d this one was a real,
already-reproduced bug — not hypothetical, and the fixture corpus (T-8) already had the evidence sitting
in it. All 80 `time.Time` fields in `commands/*.go` are on response-only structs (28 `get_*.go` files;
zero in any `create_*`/`modify_*`), populated exclusively via `encoding/xml` unmarshal through Go's stock
`time.Time.UnmarshalText` — strict RFC 3339 only, no whitespace tolerance, errors hard on empty input.
Both `iso_time` and `ctime` are declared `<pattern>text</pattern>` in `GMP.xml.in` — no `xsd:` type, no
regex, so there is no formal lexical contract, only what gvmd is observed to actually emit. Four distinct
real-world shapes already broke decoding entirely (not a dropped field — the whole response failed to
parse): an empty element (`<scan_start></scan_start>` on an imported report with no scan lifecycle), the
Java/NVD feed style with fractional seconds and a non-colon UTC offset (`2012-10-26T13:18:00.000+0000`,
seen in both `gvmd`'s own documented examples and a live capture dated 2026-08-07), a leading-whitespace-
wrapped value, and the C `ctime()` format (`Mon Feb  1 19:11:20 2010`) under a field the schema itself
mistypes as `iso_time` — confirming the schema's own type labels can't be trusted here.

Fixed with a `GMPTime` type (`commands/gmptime.go`) embedding `time.Time` — embedding rather than a bare
type conversion so `.Format()`/`.IsZero()`/etc. stay promoted — whose `UnmarshalText` trims whitespace,
treats empty as the zero value (no tri-state needed; gvmd's zero-time is never a legitimate value), and
falls back through a layout chain covering all four shapes. `MarshalText` is not redefined: these fields
are never marshalled into a real request, and the existing fidelity tooling already treats a re-marshalled
zero-value timestamp as an added element, not loss. Required one companion fix:
`internal/schema/gomodel.go`'s `structUnder`, which special-cased `time.Time` by identity so the
conformance checker would treat it as a wire scalar rather than a struct to descend into — generalized to
an `encoding.TextMarshaler`-implements check so it covers `GMPTime` too, without `internal/schema` gaining
a dependency on `commands`.

**T-5f, final regeneration, confirmed the fix**: decode-errors in `FIDELITY-SUMMARY.txt` dropped from 21 to
14, exactly the 7 fixtures identified (`live/get_info/001`, `live/get_reports/002`,

### T-6a · ~120 near-identical client methods should collapse into a generic helper
**Status:** done · **File:** `client/client.go` (1007 lines)

Every non-filtered method is the same four lines with two type names substituted:

```go
resp = new(commands.XResponse)
err = cli.conn.Execute(context.Background(), cmd, resp)
return resp, err
```

A single generic helper collapses the lot and mirrors the generic work already landed in `filtering` and
`pagination` (commits a9465b4, c2f5777, 0a3b0f0).

**Use one type parameter, not two.** `Connection.Execute(ctx, command interface{}, response
interface{})` already takes the command as `any`, so a `Req` type parameter is unconstrained, unused for
inference, and buys nothing. A second `Req` parameter only becomes meaningful in T-6b, where it carries
the constraint that binds the two types. Adding it now is speculative generality; introduce it when the
constraint arrives.

As landed, the helper takes the connection rather than the client, since it needs nothing else from
`*client`. Every example in this entry and in T-6b uses this shape:

```go
func execute[Resp any](ctx context.Context, conn gmp.Connection, cmd any) (*Resp, error) {
	resp := new(Resp)
	err := conn.Execute(ctx, cmd, resp)
	return resp, err
}
```

**Correction to an earlier draft of this entry, which claimed a wrong response type "silently
compiles". It does not.** Because every wrapper declares a concrete return type, and `New` returns
`gmp.Client` (`client/client.go:18`) so the compiler checks interface conformance, supplying the wrong
`Resp` is caught:

```go
func (cli *client) CreateTask(ctx context.Context, cmd *commands.CreateTask) (*commands.CreateTaskResponse, error) {
    return execute[commands.ModifyTaskResponse](ctx, cli.conn, cmd)
}
// cannot use execute[ModifyTaskResponse](...) (value of type *ModifyTaskResponse)
//   as *CreateTaskResponse value in return statement
```

The earlier claim came from testing a bare `execute[...]` call rather than one inside a concretely-typed
wrapper. Typed wrapper returns already close that hole, in the current hand-written code as much as in a
generic version.

**What actually does compile silently** (both verified, Go 1.23) is a mismatched *request*, and argument
transposition — because `Connection.Execute(ctx, command interface{}, response interface{})` types both
payloads as `any`:

```go
execute[commands.CreateTaskResponse](ctx, cli.conn, &commands.ModifyTask{}) // wrong cmd, right Resp — compiles
cli.conn.Execute(ctx, resp, cmd)                                       // arguments swapped — compiles
```

So the honest case for T-6a is: it removes ~500 lines of repetition, and it reduces the `any`-typed
`Execute` call from 123 hand-written sites to **one auditable site**, which is what contains the
transposition hazard. It does not add type safety the wrappers don't already provide. Closing the
wrong-request hole is T-6b's job.

No dependency on codegen; land in the same breaking release as T-3, since both rewrite every method
signature anyway.

### T-6b · Compile-time request→response binding
**Status:** todo · **Depends on:** T-9

**Acceptance criterion, stated up front:** T-6b is only worth building if there is a concrete error that
*compiles under T-6a and is rejected under T-6b*. If no such example survives contact with the real
`commands` package, **drop this entry** — generated marker methods would be pure API surface and
maintenance cost.

**That criterion is met, and has now been re-confirmed against the landed T-6a helper** rather than a
prototype. Compiled cleanly in package `client`, against the real `commands` types:

```go
execute[commands.CreateTaskResponse](ctx, cli.conn, &commands.ModifyTask{}) // COMPILES
```

The qualifying error is therefore the wrong-*request* case from T-6a (not the wrong-response case, which
typed wrappers already catch). Note the hazard is confined to the wrapper bodies themselves: no caller
outside this package can reach `execute`, and every wrapper's own signature still pins its response type.
Both halves verified on Go 1.23:

```go
// T-6a helper — func execute[Resp any](ctx, conn, cmd any) (*Resp, error)
execute[CreateTaskResponse](ctx, cli.conn, &ModifyTask{})   // COMPILES — wrong request, silently marshalled
```

```go
// T-6b helper — Req constrained to declare its own response type
type Command[Resp any] interface{ ResponseType() Resp }

func (*CreateTask) ResponseType() *CreateTaskResponse { return nil } // marker, never called
func (*ModifyTask) ResponseType() *ModifyTaskResponse { return nil }

func execute[Resp any, Req Command[*Resp]](ctx context.Context, conn gmp.Connection, cmd Req) (*Resp, error)

execute[CreateTaskResponse](ctx, cli.conn, &ModifyTask{})   // REJECTED:
// in call to execute[CreateTaskResponse], Req (type *ModifyTask) does not satisfy Command[*Resp]
//   (wrong type for method ResponseType)
//         have ResponseType() *ModifyTaskResponse
//         want ResponseType() *Resp
```

The correctly-paired call still compiles, and `Resp` is inferable, so call sites don't get noisier.

**Correction to an earlier draft of this entry:** it claimed `execute[Req]` could *derive* `Resp` from
such a marker. It cannot — Go has no associated types, so a one-type-parameter helper has no way to name
the response type in its own return signature; any attempt collapses to `any` and loses the guarantee.
The two-parameter constrained form above is the working shape.

Note the value is narrower than "type-safe commands": it closes the wrong-request hole specifically.
Whether that hole is worth ~123 marker methods is a judgement call — it is a real hazard in generated or
hand-edited wrapper bodies, but wrapper return types already catch the more common copy/paste error.
Re-confirm the criterion above against the real package before committing. What makes this depend on T-9
is volume, not feasibility: it needs ~123 marker methods, which is exactly the kind of thing codegen
emits mechanically and nobody should hand-write. An alternative worth weighing during implementation is
having codegen emit typed wrapper methods directly and leave the internal helper unconstrained — same
external safety, no constraint machinery. Prototype both against the real `commands` package before
committing; the snippets above are verified in isolation, not against 123 real types with their existing
embedding and pointer-receiver conventions.

T-6b comes *after* T-9 exists — not bundled into the same release as T-6a/T-3.

### T-7a · Confirmed: response decode failures and request encode failures share one error type
**Status:** done · **File:** `commands/errors.go`, `connections/errors.go`

Landed as specified: `ErrorType` narrowed to server-reported statuses (`ErrorTypeNetwork` removed),
`NetworkError` replaced by `RequestEncodingError` / `ProtocolError` / `TransportError`, no deprecation
shim. `GMPError` also lost `Message` (a pre-rendered duplicate of `Error()`) and `Unwrap` (it always
returned nil, which is indistinguishable from having no method — the absence now states "leaf error"
where a reader will look).

Four decisions worth keeping, because none were in the original entry:

1. **The split line is survivability, not layer.** `ProtocolError` ⟺ the connection is reusable;
   `TransportError` ⟺ it is dead. So framing failures (malformed/truncated XML) stay `TransportError`
   even though they are protocol-shaped, because they poison the connection; `ProtocolError` is only
   the boundary-known case where the document framed cleanly and the typed unmarshal failed. Routing
   both into `ProtocolError` would have merged a survivable and an unsurvivable case under one type and
   destroyed the only retryability rule callers can act on.
2. **`Error()` prefixes rather than delegating to the cause verbatim** (`encode request:`,
   `decode response:`, `transport:`). The old behaviour meant the type added nothing to the message, so
   the three failures were distinguishable only to callers writing type assertions — not to anyone
   reading a log.
3. **`ProtocolError` retains a capped 4 KiB copy of the undecodable response.** This is the evidence
   T-7b and T-8 both need, and it is already in memory at the failure site. Copied rather than aliased
   (a `get_results` response is routinely megabytes), and deliberately never included in `Error()` —
   GMP responses carry credentials.
4. **The sentinels were unreachable, and that was the real gap.** `ErrConnectionClosed`,
   `ErrConnectionBroken` and `ErrNoRawConn` live in `connections/internal/implementation`, so no
   external caller could name them. "We preserved the `Unwrap` chain" was a hollow claim while the
   chain terminated in sentinels only in-package tests could reach. `connections/errors.go` now
   re-exports them as `var` aliases, preserving error identity. Verified from a genuinely external
   module, not just in-package.

**Deliberately not changed: `ValidateResponse`.** Empty status → success and non-numeric status →
success both stay. Changing either affects all ~123 command types at once with no fixture corpus to
check against, and it belongs to T-7b, which is blocked on a live server (T-10). This is recorded so it
reads as a decision rather than an oversight.

**Deferred, not overlooked: sentinels would be more idiomatic than the enum.** Callers still write
`errors.As(err, &gmpErr)` then `switch gmpErr.Type`, where `errors.Is(err, commands.ErrNotFound)` would
read better and compose with `%w` chains for free. Narrowing the enum is a strict improvement and does
not foreclose the move, but doing it later means a third breaking change to this surface — weigh that
before 1.0.

No live server needed — this is directly readable from the code. `Execute` uses
`commands.ErrorTypeInvalidRequest` for two distinct failure modes:

```go
cmdBuf, err := xml.Marshal(command)              // line 55-57: OUTBOUND encode failure
...
err = xml.Unmarshal(resp, response)              // line 76-78: INBOUND decode failure
```

Both are wrapped as `ErrorTypeInvalidRequest`, but they mean opposite things: the first says "we
couldn't build a valid request" (a client bug, non-retryable), the second says "the server sent bytes
we couldn't parse into the expected type" (could be a server-side error envelope, a schema mismatch, a
truncated read from T-1, or a real client-library bug) — none of which is "invalid request."

The README does distinguish `GMPError` (server-side) from `NetworkError` (client-side transport) in its
prose, but its worked example only runs `errors.As(err, &gmpErr)` against `*commands.GMPError` — both of
these failures are `*commands.NetworkError`, so that example's `switch` never sees them regardless of
`ErrorType`. There's a second, smaller, independently verifiable bug in that same example: it includes a
`case commands.ErrorTypeNetwork:` arm inside the `GMPError`-typed switch, but `NewGMPError`'s status-code
mapping (`commands/errors.go:82-93`) never produces `ErrorTypeNetwork` — only `NetworkError`
construction sites do. That case arm is unreachable with the current constructors.

There is a deeper problem than the `ErrorType` value: **the type name is wrong for what it carries.**
`NetworkError` is documented as "client-side network and transport errors," but `Execute` already uses it
for XML marshalling failures (not networking) and XML decode failures (not necessarily networking).
Simply assigning better `ErrorType` constants while leaving both inside `NetworkError` keeps a misleading
hierarchy — callers who reasonably filter on `*NetworkError` to decide "is this retryable / is the link
bad" would keep catching pure client-side encoding bugs.

**Do not fix this by adding local-failure categories to `ErrorType`.** That enum exists to classify
*server-reported GMP statuses* — `NewGMPError` populates it purely from an HTTP-like status code
(`errors.go:82-93`). Adding `ErrorTypeProtocol` or a request-encoding category to the same enum merges
two unrelated domains into one type, producing combinations that can't occur (a "protocol decode
failure" with a `StatusCode`, a "404" on a marshalling bug) and making retry classification harder
rather than easier. The existing unreachable `ErrorTypeNetwork` arm is a symptom of exactly this
blending, already present.

**Fix, in four parts:**
1. Keep `GMPError` + `ErrorType` for server-reported statuses only, and *narrow* the enum to the values
   `NewGMPError` can actually produce — dropping `ErrorTypeNetwork` from it.
2. Represent local failures as distinct concrete types that do not reuse the status enum:
   `RequestEncodingError` (marshal failed), `ProtocolError` (response received but undecodable),
   `TransportError` (socket-level). This replaces `NetworkError`, whose name never covered the
   marshalling and decoding failures already routed through it.
3. Preserve `Unwrap` behaviour deliberately across the split — `NetworkError.Unwrap` returns `Cause`
   today while `GMPError.Unwrap` returns `nil`; the replacement types should make that an intentional
   choice rather than inherit it. Callers need `errors.Is(err, context.DeadlineExceeded)` to keep
   working through `TransportError`.
4. Update the README's example to run separate `errors.As` checks per type, and drop the unreachable
   `ErrorTypeNetwork` case from the `GMPError` switch.

**All of this is a breaking API change and must be scheduled as one.** `ErrorTypeNetwork` and
`NetworkError` are both exported; removing or renaming them breaks any caller that references them,
regardless of whether the value was reachable in practice. Two acceptable paths:

- **Fold T-7a into the T-3/T-6a breaking release** (preferred — the error model is part of the same
  public surface those entries are already rewriting), or
- keep compile-compatible shims for one release:
  ```go
  // Deprecated: transport failures are represented by TransportError.
  const ErrorTypeNetwork = ErrorTypeUnknown

  // Deprecated: use TransportError, ProtocolError, or RequestEncodingError.
  type NetworkError = TransportError // only viable if the field sets stay identical
  ```
  Note the alias only works if the replacement type keeps the same fields; if it doesn't, this has to be
  a clean break in the scheduled release rather than a shim.

### T-9 · Generate `commands/` from the upstream GMP schema
**Status:** in-progress · **Adopted families:** `note`, `override`, `role`, `group`, `tag`, `schedule`, `alert`, `filter`, `tls_certificate`, `permission`, `ticket` · **Review-only:** none · **Next:** re-run the rank-summing method over the remaining un-adopted create/get/modify families to pick the next candidate (`user` was next-best when `ticket` was selected) · **Source:** `gvmd/src/schema_formats/XML/GMP.xml.in`

> This entry is closer to a design document than a backlog item — problem, evidence, and a full
> migration plan are all mixed together below rather than kept to problem/evidence/acceptance
> criteria/dependencies. Left inline here rather than split out, since that split (short entry + link to

The 123 command files are hand-transcribed from the protocol docs. That does not scale across GMP
versions and quietly rots as upstream changes. Generating them would make T-5 (tri-state bools),
T-8 (fidelity), and version support fall out of one mechanism instead of three.

**Verdict: viable, ~95% mechanical, but it needs a curated exception list. Not a "run trang and go
home" pipeline.**

#### The source of truth

`src/schema_formats/XML/GMP.xml.in` — 1,259,333 bytes, ~41.9k lines. A **bespoke XML DSL**, not
XSD/RELAX-NG. Root `<protocol>` containing 155 `<command>`, 30 `<type>`, 16 `<element>`,
92 `<change>`, 4 `<deprecation>`. *(All counts independently verified against `main`.)*

There is **no `.rnc` file in the repo** — `gmp.rnc` and the published HTML reference are *build
artifacts* produced by `xsltproc` over this file, and they are strictly lossy.

**Consume `GMP.xml.in` directly. Do not go via RNC/trang/XSD.** The RNC step discards the `<summary>`
docs, the `<example>` blocks, and the `required` provenance, and it injects defects that aren't in
the source (below).

`.in` is a CMake template: it carries `@GMP_VERSION@` and feature-flag pairs
(`@IF_ENABLE_AGENTS@`…`@ENDIF_ENABLE_AGENTS@`, plus `CONTAINER_SCANNING`,
`WEB_APPLICATION_SCANNING`, `JWT_AUTH`) that must be substituted before use.

> **Better option:** pull the schema from a live server via `<help format="XML" type=""/>`. gvmd serves
> the already-configured `GMP.xml`, so this sidesteps the CMake substitution entirely *and* gives you
> the schema for the exact server version you're talking to. It also avoids vendoring (see licensing).

#### The DSL maps cleanly onto Go

| tag | meaning | Go |
|---|---|---|
| `<e>x</e>` | required child | field |
| `<o><e>x</e></o>` | optional | pointer + `omitempty` |
| `<any><e>x</e></any>` | zero-or-more | slice |
| `<attrib>` | attribute | `,attr` (+ `omitempty` unless `<required>1</required>`) |
| `<alts><alt>` | enum | const block |
| `<g>` / `<or>` | interleave / choice | struct / variant |

Cardinality is exactly {1, 0..1, 0..n} — there is no `+` and no `minOccurs/maxOccurs`. Attrs-vs-children
is unambiguous. Pointer-vs-value and `omitempty` are directly derivable, which is precisely what fixes
T-5 mechanically.

Encouraging sanity check: the schema's `create_tag` maps 1:1 onto the existing hand-written
`commands/create_tag.go`, down to `Resources *CreateTagResources` and
`Filter string \`xml:"filter,attr,omitempty"\``. **The hand-written code is essentially what a generator
would emit** — which is the best possible signal that this is worth doing.

Bonus: **206 worked request/response examples covering 154 of 155 commands**, plus 4,271 `<summary>`
strings. The examples are free golden-test fixtures for T-8 (subject to licensing, below).

#### Known defects — the exception list

All verified against `main` today:

1. **~85 sites write `<pattern><type>text</type></pattern>` instead of `<t>text</t>`.** The XSL has no
   `type` branch, so the generated RNC emits a literal `ERROR`. Harmless if you consume the XML directly
   and treat `<type>` as a synonym for `<t>` — but fatal if you route through RNC.
2. **68 dangling `<e>` references** with no `<ele>` definition, concentrated in the newest commands:
   `get_scan_report` (18), `get_agent_groups` (15), `get_report_tls_certificates` (14),
   `get_integration_configs` (13).
3. **`get_filters` is structurally broken** — references a nonexistent `filters2` element and defines
   `<ele>filters</ele>` twice, producing invalid RELAX NG. Reported as
   [gvmd#541](https://github.com/greenbone/gvmd/issues/541) in 2019, closed 2021 *without the fix landing*.
4. **52 completely empty `<pattern/>`** — e.g. `task/config/permissions`. Pure hand-waving.
5. **8 undefined type names** needing an alias table: `UUID` (31×, wrong case), `real` (9×), `number` (3×).
6. **`boolean` is `text`, not a boolean.** Schema note: *"Zero is false, anything else is true. As a
   result, the empty string is considered true"* — and `boolean_atoi` is the **opposite**. Mapping
   either to Go `bool` needs a custom marshaler; a naive `bool` is wrong. Directly relevant to T-5.
7. **Upstream CMake bug:** `@ENDIF_ENABLE_CREDENTIAL_STORES@` appears twice with **no matching
   `@IF_ENABLE_CREDENTIAL_STORES@`** *(independently confirmed: 2 closers, 0 openers)*. With credential
   stores disabled, the generated XML is malformed.
8. **No shared type reuse.** The 16 top-level `<element>` definitions are never referenced by any
   command; everything is copy-pasted inline. 2,989 `<ele>` definitions but only 537 distinct names
   (`name` redefined 321×, `comment` 107×). Naive generation yields ~3,300 near-duplicate Go types —
   **structural hashing + dedup is where most of the generator's real work lives.**
9. **Requests are over-constrained.** `create_task` marks `config`/`target`/`scanner` required with no
   `<or>`, though the agent/OCI variants clearly replace `target`. Trust response-side optionality more
   than request-side.

#### Version drift — this is already biting

The schema tracks gvmd's branch, so output is version-pinned. Concrete: **`hosts_ordering` appears 8× in
`v23.9.0` and zero times in `main`** *(verified)* — yet `commands/create_task.go:15` has
`HostsOrdering`. **You are already targeting an older GMP than upstream `main`, without recording which
one.** Generate per-tag and diff; the 92 `<change>` and 4 `<deprecation>` entries are a machine-readable
migration log, and this is what finally lets you publish the compatibility matrix T-12 wants.

#### Prior art: none

- **python-gvm is fully hand-maintained** — no reference to `schema_formats` anywhere.
- **No Go project generates from this schema**, including the `filewalkwithme/go-gmp` this project
  is based on.
- The only recorded attempt (gvmd#541, Java, via RNC) failed on exactly the defects above.

You'd be first. That's an opportunity, but it also means no one has de-risked this for you — which is
why the conformance-report step below matters.

#### Recommended approach

1. **Do this after T-8/T-10.** Codegen without a fidelity oracle just changes *who* wrote the wrong tags.
2. **First deliverable is a conformance report, not generated code** — diff the schema-derived model
   against the existing 123 structs. Finds real bugs immediately, at a fraction of the cost, and proves
   the generator understands the DSL before anything depends on it.
3. Keep the generator out of the published module (`internal/cmd/gen` or the empty `scripts/`).
4. Only then migrate packages to generated output, one at a time, with golden tests as the gate.

### T-13 · No connection lifecycle management, and poisoning is broader than just cancellation
**Status:** in-progress — the boundary-known/unknown poisoning classification and the write-count
check are done (`connections/internal/implementation/conn.go`); reconnect, keepalive, backoff, and a
public `Client.Close()` remain

No reconnect, no keepalive, no retry/backoff, and no re-authentication after a dropped connection.

Context cancellation is the *obvious* poisoning case — `Execute` deliberately closes the socket on
`ctx.Done()`, permanently killing the `Connection` for every later call with no recovery path — but
it's not the only one, and framing this as only a cancellation problem understates the scope. The
distinguishing question for each failure is whether it leaves message-boundary position **known** or
**unknown** — only the latter requires poisoning the connection:

- **Any partial write** (deadline hit mid-write, transient network error) leaves the server having
  received a fragment of a command. The client doesn't know whether the server will act on it, ignore
  it, or hang waiting for the rest — boundary unknown, poison.
- **Any read timeout, EOF before the root closes, or malformed/unframeable XML** (see T-1) leaves the
  socket's read position at an unknown point relative to message boundaries. If the connection is
  reused, the *next* `Execute` call may read the tail of the previous, still-in-flight response and
  misinterpret it as its own — silent data corruption, not just an error — boundary unknown, poison.
- **A fully-framed document that fails typed `xml.Unmarshal`** is different, once T-1 lands: decoder-based
  framing means the root element's matching `EndElement` was already consumed cleanly, so the *stream*
  position is known — the reader is correctly positioned at the start of whatever comes next. Only the
  *decode into a concrete Go type* failed, which is a schema/version-drift signal (T-7a/T-9), not a
  transport-safety one. Poisoning the connection on every such mismatch would kill perfectly usable
  connections on ordinary version drift. Do not poison here; surface the typed decode error and leave
  the connection usable.

For the boundary-unknown cases, retrying on the same stream is unsafe because protocol synchronization
is no longer known. **Any transport/protocol failure that leaves message-boundary position ambiguous
must mark the connection permanently unusable** — but a clean decode failure into the wrong struct must
not. Reconnect/re-authentication, when added, must always happen on a fresh connection — never by
resuming reads/writes on one that hit an ambiguous failure.

**Related, currently unhandled: the write return count is discarded.** `performRequest` does
`_, err := conn.rawConn.Write(buffer)` (`conn.go:26`) and never checks `n`. `io.Writer`'s contract does
require implementations to return a non-nil error whenever `n < len(p)` — but that is an obligation on
the *implementation*, and checking `n` is the caller's obligation regardless. It is not merely
defensive: `io.WriteString`, wrapper types, and above all **this repo's own hand-written test mocks**
(every test runs against them — T-10) can and do exhibit short-write behavior that a real TCP socket
would not. Beyond that, the *real* defect the discard hides is that when `Write` fails after
transmitting some bytes, the current code returns the error and leaves the connection fully reusable —
precisely the ambiguous-partial-write case above. Acceptance criteria:

- check `n == len(buffer)`; treat a short write as ambiguous (`io.ErrShortWrite`) and poison;
- poison on *any* write error, since partial transmission cannot be ruled out;
- do not silently retry the remainder — resuming a half-sent command is only safe if retry semantics are
  deliberately designed, which they are not today.

**State handling lives in T-2b, not here.** A single unsynchronized `broken` bool is both racy (once
T-2 lands) and too coarse; the `open`/`broken`/`closed` model, its ownership rules, and how it interacts
with `Close` are specified in T-2b. T-13's contribution is the *classification* above — which failures
justify the `open → broken` transition and which do not.

`Client` also exposes no `Close()`, so callers must hold the `Connection` separately to shut down.
